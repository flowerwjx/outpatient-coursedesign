## 1. 审查结论摘要

整体安全基线较好：

- 密码使用 bcrypt 加盐哈希；
- 使用 JWT 鉴权，并在服务端校验用户角色；
- 业务接口使用 `require_role` 做 RBAC；
- 收费金额由后端读取药品档案单价计算；
- 挂号、收费、发药使用事务和原子更新；
- 全局审计中间件覆盖写操作；
- CORS 未使用通配符，JWT 密钥从环境变量读取。

但当前版本更适合课程演示和内网环境，若直接用于生产，仍存在以下重点风险：

1. 默认演示账号和密码重置脚本；
2. SQLite 外键约束默认未启用；
3. 登录无限速、JWT 无撤销机制；
4. 审计日志可被数据库层篡改，审计失败被静默忽略；
5. 患者姓名、手机号、诊断等 PII 存储和审计未做脱敏/保留策略；
6. 部分查询接口返回全量患者数据；
7. 缺少 HTTPS、安全响应头和生产级限流。

**总体判断：课程演示环境可接受；生产部署前应优先修复高危和中危问题。**

## 3. 安全审查问题表

| 问题描述 | 风险等级 | 人工复核结论 | 修复建议 |
|---|---|---|---|
| SEC-01 默认演示账号与密码重置脚本：`scripts/init_user.py` 内置四类账号固定密码，脚本每次运行都会重置密码，并向标准输出打印明文密码。 | 高危 | 确认。代码与前端登录页均存在演示账号；课程演示可接受，生产环境不可接受。 | 生产环境删除默认账号和演示密码；首次登录强制改密；禁止在日志中打印明文密码；初始化脚本增加环境限制和二次确认。 |
| SEC-02 登录接口无失败次数限制、账号锁定或验证码：`routers/auth.py` 的登录接口可被持续尝试。 | 中危 | 确认。当前仅做密码校验，没有登录限速、锁定或异常登录告警。 | 增加基于 IP/账号的登录限速、失败次数锁定、告警和必要的验证码；记录失败登录审计并监控。 |
| SEC-03 JWT 无撤销机制：退出登录只清理前端 token，服务端没有黑名单、jti 或 token 版本控制，token 在过期前仍可使用。 | 中危 | 确认。`middleware/auth.py` 只校验签名、过期时间和数据库角色，无撤销列表。 | 增加 `jti` 和 token 黑名单/版本号；缩短 access token 有效期；必要时引入 refresh token 和主动失效机制。 |
| SEC-04 SQLite 外键约束默认未启用：`database.py` 未设置 `PRAGMA foreign_keys=ON`，模型声明的外键在 SQLite 中默认不生效。 | 中危 | 确认。使用当前引擎实测 `PRAGMA foreign_keys` 返回 `0`。 | 在 SQLite 连接事件中执行 `PRAGMA foreign_keys=ON`；增加外键约束测试；生产环境优先使用支持完整外键的数据库。 |
| SEC-05 审计日志可被数据库层篡改：`audit_logs` 与业务表共用 SQLite，拥有数据库文件权限的人可以直接修改或删除审计记录，没有只追加约束或哈希链。 | 中危 | 确认。当前只有应用层“不提供修改/删除接口”，没有数据库层防篡改。 | 限制数据库文件权限；审计表使用只追加权限；增加哈希链/签名；生产环境将审计日志同步到独立日志系统。 |
| SEC-06 审计写入失败被静默忽略：`middleware/audit.py` 对审计写库异常执行 `db.rollback()` 后不抛错，业务请求仍会成功。 | 中危 | 确认。审计表不可用或写满时，关键写操作可能没有审计记录。 | 对高风险操作采用“审计失败则业务失败”或可靠 outbox/重试；至少增加告警和审计失败监控。 |
| SEC-07 审计载荷包含患者 PII：挂号、处方、收费等 JSON 请求体会被写入 `payload`，包含患者姓名、手机号、诊断等信息；当前只对 password/token/secret 脱敏。 | 中危 | 确认。审计中间件会记录请求体摘要，未对患者姓名、手机号、诊断做脱敏。 | 对审计载荷做字段级脱敏或只记录必要业务标识；设置审计日志保留期限和访问审批；审计表加密或受限访问。 |
| SEC-08 审计中间件读取完整请求体，缺少全局请求体大小限制：`await request.body()` 先读取完整 body，药品 CSV 的 5MB 限制发生在路由读取之后；未认证写请求也会触发审计写入。 | 中危 | 确认/部分确认。代码层面没有全局 body 限制；Docker Nginx 有 10MB 限制，但直接访问后端时不受该限制保护。 | 在 ASGI/Nginx/网关层统一限制请求体大小；对写请求增加限流；审计日志增加容量监控和清理策略。 |
| SEC-09 患者数据读取范围过宽：`GET /api/registrations` 对所有登录用户开放；`GET /api/prescriptions` 对 cashier/pharmacist 开放全部记录，返回患者姓名、手机号和诊断。 | 中危 | 确认（按当前课程需求部分可接受）。接口有角色鉴权，但没有行级数据范围限制，药师/收费员可查询全部患者数据。 | 按角色最小化字段和记录范围；医生只看本人患者，药师只看待发药/已发药处方，收费员只看收费相关数据；增加审计和分页。 |
| SEC-10 缺少患者数据读访问审计：审计中间件只记录 POST/PUT/PATCH/DELETE，没有记录谁查询了患者信息、处方或收费记录。 | 低危 | 确认。当前只审计写操作，读访问不可追溯。 | 对敏感读接口增加访问审计或网关访问日志；注意读日志同样需要 PII 脱敏和保留策略。 |
| SEC-11 数据库与 PII 静态明文存储：SQLite 文件和患者信息未加密，且缺少定时备份/恢复策略。 | 中危 | 确认。数据库文件权限依赖宿主机和容器配置，未实现静态加密和备份。 | 限制数据库文件权限；启用磁盘/卷加密；建立加密备份和恢复演练；生产环境评估加密数据库或字段级加密。 |
| SEC-12 缺少 HTTPS 和安全响应头：`frontend/nginx.conf` 仅监听 80，未配置 TLS、HSTS、CSP、X-Frame-Options、X-Content-Type-Options 等。 | 中危 | 确认。本地课程演示可接受；公网部署会把 token 和患者数据暴露在明文链路上。 | 生产环境启用 HTTPS/TLS；配置 HSTS、CSP、X-Frame-Options、X-Content-Type-Options、Referrer-Policy；限制访问来源。 |
| SEC-13 后端容器以 root 运行：`backend/Dockerfile` 未设置 `USER`，容器默认使用 root。 | 低危 | 确认。当前 Dockerfile 没有非 root 用户。 | 创建专用非 root 用户并切换 `USER`；限制容器 capabilities、只读文件系统和最小权限卷挂载。 |
| SEC-14 FastAPI 文档和 OpenAPI 默认暴露：`main.py` 未关闭 `/docs`、`/redoc`、`/openapi.json`。 | 低危 | 确认。Docker 部署中后端未直接暴露，但本地运行或直接暴露后端时文档可访问。 | 生产环境设置 `docs_url=None`、`redoc_url=None`、`openapi_url=None`，或仅对受信网络开放。 |
| SEC-15 JWT 算法和密钥强度缺少强制约束：`config.py` 允许环境变量改变 `JWT_ALGORITHM`，未做算法白名单；未校验 `JWT_SECRET` 最小长度和复杂度。 | 低危 | 部分确认。代码没有硬编码密钥，密钥来自环境变量；但配置错误时缺少防护。 | 固定允许算法为 HS256（或明确白名单）；启动时校验密钥最小长度/熵；建立密钥轮换流程。 |
| SEC-16 密码策略较弱：`hash_password` 只要求非空且不超过 72 字节，登录 schema 只要求长度 ≥1，没有复杂度、轮换和首次登录改密要求。 | 低危 | 确认。密码哈希本身安全，但账号口令策略不足。 | 增加密码最小长度/复杂度/黑名单；首次登录强制改密；定期轮换；禁止使用演示密码。 |
| SEC-17 CSV 单价校验不完整：`drug_service._parse_drug_row` 只校验非负和最多 2 位小数，没有限制最大位数/上限；API 的 `DrugCreate` 使用 `max_digits=10`，两者不一致。 | 低危 | 确认。恶意或错误 CSV 可写入超大单价值，影响金额计算和数据质量。 | CSV 解析复用 Pydantic `DrugCreate` 校验，或补充 `max_digits`、上限和 Decimal 上下文；失败行返回明确错误。 |
| SEC-18 CSV 导入回显内部异常：`drug_service.import_drugs_from_csv` 的兜底异常把 `f"导入失败: {exc}"` 返回给调用方。 | 低危 | 确认。可能向管理员/药师泄露数据库或实现细节。 | 对外返回通用错误码/行号，内部日志记录详细异常；区分校验错误和系统错误。 |
| SEC-19 排班修改与挂号并发可能丢失号源更新：`schedule_service.update_schedule` 先读取已用号源，再写入新的 `remaining_quota`；与挂号原子扣减并发时可能覆盖最新号源。 | 中危 | 确认（代码级并发风险，未做并发压测）。当前事务粒度下存在丢失更新窗口。 | 使用行锁/乐观锁版本号；或将剩余号源变更改为数据库原子表达式；增加并发测试；限制排班修改与挂号并发窗口。 |
| SEC-20 `prescription_items.drug_id` 没有数据库外键：模型只保存逻辑药品 ID；当前 SQLite 外键又未启用，可能产生孤儿引用。 | 低危 | 确认。收费和发药业务层会校验药品存在，但数据库层没有强制引用完整性。 | 为 `drug_id` 增加外键；启用 SQLite 外键；对历史数据做完整性巡检；删除药品前检查引用。 |
| SEC-21 Nginx 访问日志可能记录 PII：挂号、处方查询接口支持 `phone`、`patient_name` 查询参数，Nginx 默认访问日志会记录完整请求 URI。 | 低危 | 确认。风险取决于是否使用查询参数以及访问日志保留策略。 | 避免在 URL 中传递患者敏感信息；Nginx 关闭查询字符串日志或做脱敏；限制访问日志权限和保留期。 |
| SEC-22 依赖版本未锁定且生产镜像包含测试依赖：`requirements.txt` 使用 `>=` 范围；后端镜像安装 pytest、httpx 等测试依赖，未做依赖漏洞扫描。 | 低危 | 确认。当前没有 lock 文件、哈希校验或 CVE 扫描流程。 | 使用锁定版本/哈希；拆分生产依赖；定期执行依赖漏洞扫描；固定基础镜像 digest。 |
| SEC-23 缺少全局 API 限流：除登录外，收费、发药、CSV 导入、审计查询等接口没有统一限流。 | 低危 | 确认。当前仅有角色鉴权，没有请求频率限制。 | 在网关/Nginx/应用层增加按角色和 IP 的限流；对昂贵查询和写操作单独限流。 |
| SEC-24 审计日志缺少客户端上下文：未记录客户端 IP、User-Agent、request-id，取证能力有限。 | 低危 | 确认。审计字段只包含操作人、时间、路径、方法、状态码和载荷。 | 增加 request-id、客户端 IP、User-Agent；注意 IP 和 UA 也属于日志敏感信息，需脱敏和保留策略。 |
| SEC-25 CSV 公式注入风险（未来导出场景）：当前没有 CSV 导出功能，暂不可触发；若未来增加导出，药品名称等字段以 `=`、`+`、`-`、`@` 开头可能在 Excel 中被执行。 | 提示 | 部分确认。当前无导出入口，属于前瞻性风险。 | 未来导出时对可疑前缀加单引号或转义；限制导出权限并记录审计。 |
| SEC-26 `.env` 密钥文件权限和轮换未强制：密钥从 `.env` 读取，`.gitignore` 已忽略 `.env`，但代码未校验文件权限或轮换周期。 | 低危 | 部分确认。密钥未硬编码，但部署层缺少强制保护。 | 设置 `.env` 最小文件权限；使用 secret manager；定期轮换 JWT 密钥并支持多密钥过渡。 |
| SEC-27 演示药品初始化脚本可能覆盖生产数据：`scripts/init_drugs.py` 对已存在药品执行更新，会把单价和库存重置为演示值。 | 低危 | 确认。脚本用于课程演示，误在生产执行会破坏库存和价格。 | 脚本增加环境检查/二次确认；生产禁止运行演示初始化脚本；将演示数据与生产数据初始化分离。 |

## 5. 修复优先级建议

### P0：生产部署前必须处理

1. 删除默认演示账号，禁止脚本打印明文密码。
2. 启用 SQLite 外键约束，或迁移到支持完整约束的数据库。
3. 登录限速、失败锁定和异常登录告警。
4. JWT 撤销机制、较短有效期和密钥强度校验。
5. 审计日志防篡改、审计失败告警和 PII 脱敏/保留策略。

### P1：生产部署前应处理

1. 患者数据最小化访问和行级权限控制。
2. 数据库/PII 加密与备份恢复。
3. HTTPS、安全响应头和网络边界限制。
4. 请求体大小限制、全局 API 限流。
5. 排班修改与挂号并发的号源一致性。
6. 为 `prescription_items.drug_id` 增加引用完整性约束。

### P2：持续改进

1. 非 root 容器、只读文件系统、最小权限。
2. 关闭生产环境 API 文档。
3. 锁定依赖版本、拆分生产依赖、依赖漏洞扫描。
4. 审计日志增加 IP/UA/request-id 和访问日志脱敏。
5. CSV 导入复用统一校验，避免规则分叉。
6. 增加读访问审计和日志保留策略。

## 6. 审查结论

本项目在课程设计范围内具备较好的基础安全实践：密码哈希、JWT 鉴权、RBAC、事务、原子库存扣减、后端计价和全局审计均已落地。

但当前版本仍属于课程演示/内网部署级别，不建议直接作为生产医疗系统上线。生产化前应优先处理默认账号、SQLite 外键未启用、登录限速、JWT 撤销、审计防篡改和患者 PII 保护等问题。

> 说明：本报告为代码级人工审查结果，未执行渗透测试、依赖 CVE 扫描和实际攻击验证；实际风险应结合部署环境、网络边界和运维权限综合评估。
