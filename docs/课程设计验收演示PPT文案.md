## 第 2 页：项目概述

### 页面标题

**项目概述：依据 2002 版 HIS 规范构建门诊业务闭环**

### 页面文案

- 设计依据：《医院信息系统功能规范（2002 版）》
- 面向场景：小型门诊、单院区、门诊核心业务
- 核心目标：
  - 挂号号源事务扣减
  - 医生 ICD-10 诊断开方
  - 收费金额后端计算
  - 药房发药库存扣减
  - 全流程审计可追溯
- 业务闭环：

```text
管理员排班 → 患者挂号 → 医生接诊开方 → 收费员收费 → 药师发药 → 审计与统计
```

### 2002 版规范对应关系

| 2002 版规范领域 | 本项目模块 |
|---|---|
| 门诊挂号 | 排班、号源查询、挂号记录 |
| 门诊医生工作站 | 待接诊患者、ICD-10 诊断、处方明细 |
| 门诊收费 | 后端划价、收费单、处方已收费状态 |
| 药房管理 | 药品档案、CSV 导入、发药、库存扣减 |
| 统计报表 | 今日挂号量、今日收费金额 |
| 系统管理 | JWT、RBAC、全局审计日志 |

### 口播稿

本项目不是简单做增删改查，而是按照 2002 版 HIS 规范，把门诊业务串成一条闭环链路。患者从挂号开始，经过医生诊断开方、收费、药房发药，最后形成审计和统计结果。每个环节都对应规范中的门诊子系统要求。

## 第 3 页：系统总体架构与角色说明

### 页面标题

**系统总体架构与角色权限设计**

### 总体架构

```text
Vue3 前端
   ↓
Nginx（静态资源 + /api 反向代理）
   ↓
FastAPI 后端
   ├─ JWT 鉴权
   ├─ RBAC 角色权限
   ├─ 业务 Service 层
   ├─ 全局审计中间件
   └─ SQLAlchemy ORM
   ↓
SQLite 持久化数据库
```

### 技术架构说明

- 前端：Vue3 + Vite，按角色显示不同工作台
- 后端：FastAPI + SQLAlchemy，分层为 models、schemas、services、routers
- 数据库：SQLite，Docker 部署时挂载持久化目录
- 安全：JWT + RBAC + bcrypt + 审计中间件
- 部署：Docker Compose 编排前后端，Nginx 代理 `/api`

### 角色说明

| 角色 | 主要职责 |
|---|---|
| admin 系统管理员 | 排班维护、药品维护、CSV 导入、审计查询、统计报表、挂号 |
| doctor 门诊医生 | 查看本人待接诊患者、创建处方、填写 ICD-10 诊断 |
| cashier 收费员 | 挂号、查询未收费处方、收费预览、执行收费、收费记录 |
| pharmacist 药房药师 | 药品档案查看、CSV 导入、已收费处方发药 |

### 关键权限边界

- 排班 CRUD：仅 admin
- 创建挂号：仅 admin、cashier
- 创建处方：仅 doctor
- 执行收费：仅 cashier
- 执行发药：仅 pharmacist
- 审计查询：仅 admin
- 统计报表：仅 admin

### 口播稿

系统采用前后端分离架构。前端通过 Nginx 访问后端 `/api`。后端所有接口都经过 JWT 鉴权和角色权限校验。四个角色职责清晰：管理员维护基础数据和审计，医生负责诊断开方，收费员负责收费，药师负责发药。

## 第 8 页：安全设计：RBAC、越权拦截与密码哈希

### 页面标题

**安全设计：JWT + RBAC + bcrypt + 全局审计**

### 页面文案

#### RBAC 权限

| 功能 | admin | doctor | cashier | pharmacist |
|---|---|---|---|---|
| 排班维护 | 允许 | 禁止 | 禁止 | 禁止 |
| 创建挂号 | 允许 | 禁止 | 允许 | 禁止 |
| 创建处方 | 禁止 | 允许 | 禁止 | 禁止 |
| 执行收费 | 禁止 | 禁止 | 允许 | 禁止 |
| 执行发药 | 禁止 | 禁止 | 禁止 | 允许 |
| 审计查询 | 允许 | 禁止 | 禁止 | 禁止 |
| 统计报表 | 允许 | 禁止 | 禁止 | 禁止 |

#### 越权拦截

- 未登录访问受保护接口：HTTP 401
- 角色不匹配：HTTP 403
- 前端隐藏入口只是体验层，后端权限才是最终防线

#### 密码安全

- 密码使用 bcrypt 加盐哈希
- 数据库只保存 `password_hash`
- 禁止明文密码
- JWT 密钥从环境变量读取，不硬编码

#### 审计安全

- POST / PUT / PATCH / DELETE 自动审计
- 业务代码不手动写日志
- 敏感字段脱敏

### 截图建议

建议放两张截图：

1. doctor 调用挂号 POST 返回 403
2. 数据库用户表中 `password_hash` 字段示例，注意打码，不要展示真实密钥

截图重点标注：

- 403 越权拦截
- bcrypt 哈希前缀 `$2b$`
- 没有明文密码

### 口播稿

安全设计上，系统使用 JWT 做认证，使用 RBAC 做角色鉴权。比如医生直接调用挂号接口会返回 403。密码使用 bcrypt 加盐哈希，数据库不保存明文密码。所有写操作由中间件自动写入审计日志，业务代码不需要手动写日志。

## 第 9 页：数据规范：药品五要素、CSV 导入与 ICD-10

### 页面标题

**数据规范设计：药品五要素、CSV 校验与 ICD-10**

### 页面文案

#### 药品五要素

药品档案必须包含：

1. 通用名
2. 商品名
3. 规格
4. 剂型
5. 医保类别

并增加：

- 单价 `unit_price`
- 库存 `stock`
- 数据库约束：`stock >= 0`、`unit_price >= 0`

#### CSV 批量导入

- 支持 UTF-8 / GB18030
- 兼容中英文表头
- 服务端逐行校验
- 缺失必填项、非法数值、重复药品标记为错误行
- 错误行不影响合法行入库
- 返回成功数量、失败数量、逐行错误原因

#### ICD-10 编码

- 处方必须保存 `icd10_code`
- 同时保存诊断中文名称
- 后端校验编码格式，例如 `J06.9`
- 统一转换为大写
- 示例：
  - J06.9 急性上呼吸道感染
  - I10 原发性高血压
  - E11.9 2 型糖尿病

#### 数据完整性

- 一个挂号一张处方
- 一个处方一张收费单
- 一个处方一次发药
- 同一处方内药品不重复
- 处方数量大于 0

数据规范方面，药品档案严格包含五要素，并增加单价和库存。CSV 导入采用服务端逐行校验，错误行不会影响合法行。处方必须保存 ICD-10 编码和诊断名称，后端会做格式校验和统一大小写处理。

## 第 11 页：AI 开发复盘：最难 Bug、提示词迭代与人工修改

### 页面标题

**AI 开发复盘：从“能跑”到“可验证、可回滚”**

### 页面文案

#### 最难 Bug

**发药多药品库存扣减的事务风险**

- 处方包含多个药品
- 如果逐条扣库存，前一药品已扣，后一药品库存不足
- 可能出现部分扣减、库存不一致

#### 第一轮提示词

```text
实现发药接口：遍历处方明细扣减 drug.stock；库存不足返回 400。
```

#### AI 第一次输出的缺陷

- 逐条 ORM 扣减库存
- 没有 `stock >= qty` 原子条件
- 库存扣减和发药记录没有放在同一个事务
- 异常时可能只回滚当前操作

#### 第二轮迭代提示词

```text
请加固发药库存扣减：
1. 处方必须 paid=True；
2. 防止重复发药；
3. 先校验所有明细库存；
4. 使用 UPDATE drugs SET stock=stock-qty WHERE id=? AND stock>=qty；
5. 任一药品不足，整个事务 rollback；
6. 库存扣减和 DispenseRecord 创建必须在同一个 commit；
7. 补充库存不足、多药品回滚、重复发药测试。
```

#### 人工修改点

- 文件：`backend/app/services/dispense_service.py`

### 口播稿

## 第 12 页：不足与改进：如果重新开发怎么做

### 页面标题

**不足与改进：如果重新开发，我会怎么做得更好**

### 页面文案

#### 当前不足

1. SQLite 外键约束默认未启用
2. 登录无限速、无账号锁定
3. JWT 无撤销机制，退出登录后 token 到期前仍有效
4. 审计日志可被数据库层篡改，审计失败被静默忽略
5. 患者姓名、手机号、诊断等 PII 未加密、审计未脱敏
6. 缺少 HTTPS、安全响应头和生产级限流
7. 尚未实现 Playwright E2E、定时备份和完整用户管理页面

#### 如果重新开发

| 方向 | 改进方案 |
|---|---|
| 数据库 | 使用 PostgreSQL/MySQL；引入 Alembic 迁移；启用完整外键约束 |
| 安全 | 登录限速、账号锁定、JWT 撤销、密钥轮换、HTTPS、安全响应头 |
| 审计 | 审计日志独立存储、哈希链防篡改、PII 脱敏和保留策略 |
| 权限 | 行级数据权限，医生只看本人患者，药师只看发药范围 |
| 并发 | 排班修改与挂号并发使用行锁/乐观锁 |
| 测试 | 增加 Playwright E2E、并发测试、备份恢复测试、依赖漏洞扫描 |
| 运维 | 定时备份、监控告警、非 root 容器、生产环境关闭 API 文档 |
| 业务 | 增加退费、退号、药品批次、效期和盘点管理 |

#### 答辩第三问回答

如果重新开发，我会把安全、事务和测试前置到设计阶段，而不是最后补；数据库优先选择支持完整约束的 PostgreSQL；审计和 PII 保护作为独立模块设计；并发场景先用测试复现，再实现行锁或原子更新。

### 口播稿

这一页回答如果重新开发怎么做。当前项目作为课程设计已经实现核心闭环，但生产化还有不足。重新开发时，我会优先换用 PostgreSQL，启用完整外键；把登录限速、JWT 撤销、审计防篡改和 PII 保护前置设计；同时补充 E2E、并发和备份恢复测试。
